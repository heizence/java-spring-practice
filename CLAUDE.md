# CLAUDE.md — java-spring-practice

Rules for anyone (human or AI) who **writes or maintains the practice material** in this repository.
Learners don't need this file; their guide is `README.md`.

## What this is

A lifelong practice workspace for one learner: a backend engineer who works in Spring Boot, is fluent in
TypeScript/JavaScript, and wants Java and Spring fluency.

- **Time budget:** 30 minutes on weekdays, 60 minutes on weekends and holidays. About 13 weeks for the core path.
- **Part 1 — Java** (`java/j01` … `j10`): language basics → advanced, data structures as concepts, concurrency,
  reflection, a mini DI container. Not coding-test practice.
- **Part 2 — Spring Boot** (`spring/s01` … `s14`, stages 2 and 3): core concepts (IoC/DI, AOP, web, JDBC/JPA,
  transactions/ACID, locking, events, caching, HTTP clients, security, testing, production readiness) on one
  bookstore domain with MySQL. No Redis/Kafka/RabbitMQ (possible electives later).
- **All learner-facing text is in English**: plain words, short sentences, active voice, no idioms. Define a term
  the first time you use it. Address the reader as "you". Don't write "simply", "just" or "obviously".

### Versions (all in `gradle/libs.versions.toml`)

Java 25 (Gradle toolchain; downloaded automatically by the foojay resolver if missing) · Gradle 9.8 wrapper,
Kotlin DSL · JUnit 6 · AssertJ 3 · Mockito 5 · Spring Boot 4.1.x and MySQL 9.7 LTS for Part 2.

## Exercise types

The line under each README exercise heading starts with one of these, in bold.

| Type | The learner… | On `main` | In `.solutions/` |
|---|---|---|---|
| **Build** | implements stubs until the tests pass | stubs + tests | implementation + ≥ 2 verification mutants |
| **Predict** | writes predictions in an answer sheet, then runs the tests | `Puzzles` + `Answers` (all `null`) + tests | `Answers` filled in, one-line explanation each |
| **Fix** | finds and fixes bugs in realistic code | buggy code + failing tests | fixed code + ≥ 2 verification mutants (plausible wrong or half fixes) |
| **Write tests** | writes tests for finished, correct code | correct code + empty test class + ≥ 4 learner mutants in `src/mutants` | reference tests that catch every learner mutant |

## Conventions the tooling depends on

1. **IDs and packages.** Exercise `J05-09` lives in package `practice.j05.ex09` (Part 2: `S03-02` → `practice.s03.ex02`).
   Sub-packages are fine (`practice.j09.ex04.sample`).
2. **README headings are the catalog.** Each exercise has exactly one heading `### J05-09 · LRU cache`, followed by
   a line like ``**Build** · 30 min · [`File.java`](src/main/java/…)``. An optional exercise ends its title with ` ★`.
   The module title is the first `# ` heading, formatted `# J05 · Collections and data structures`.
3. **One top-level test class per exercise**, annotated `@DisplayName("J05-09 · LRU cache")` (same title as the README).
   An exercise may have more than one test class only if each carries the same display name.
4. **Tiers are `@Nested` classes** with `@DisplayName("Basic")`, `"Edge cases"`, `"Errors"`, and where useful
   `"Randomized"` or `"Concurrency"`. Predict exercises group puzzles by topic instead. Another tier name is fine
   when an exercise needs it (J04-02 has "Signatures"); the score report lists unknown tiers last.
5. **Every test has a `@DisplayName`** that states the behavior in plain English: "rejects a capacity below 1",
   "returns empty for a key that was never stored". The learner sees failing test names as hints.
6. **Stubs** keep the solution's exact public API and Javadoc. Each body is
   `// TODO: J05-09` plus `throw new UnsupportedOperationException("TODO: J05-09");`. Stubs must compile; fields
   may be left out. The Javadoc is the spec: it states every rule, including edge cases and errors.
   Exception: when the signature itself is the exercise (J04-02, wildcards), the stub has a deliberately strict
   signature, the tests check the generic signature through reflection, and behavior tests only make calls that
   compile against both versions. A compile error in a test file would block the whole module.
7. **Every exercise starts failing** on `main` (at least one failing test; Write tests: no tests yet) and is fully
   green with its solution. `scripts/verify.sh` checks both.
8. **Mutants** are whole-file copies of a class with one realistic mistake:
   `src/mutants/<exNN-short-name>/java/<package path>/<Class>.java` plus `mutant.properties`:
   ```properties
   package=practice.j05.ex09
   audience=verification
   description=Evicts in insertion order (FIFO) instead of least recently used order.
   ```
   Learner mutants (`audience=learner`) also need a `hint=` that points at the gap without giving the test away.
   Every mutant must compile and must be caught by the reference tests. Prefer mistakes people really make
   (off-by-one, missing null check, wrong boundary, shared mutable state, missing defensive copy, wrong lock order).
   Each mutant directory name starts with the exercise number (`ex09-…`), because one module's mutants share a folder.

## Writing exercises

### Size

A weekday exercise takes **about 30 minutes** for someone who knows TypeScript well but is new to Java: reading the
lesson section, implementing roughly 3–6 small methods, running tests. A weekend exercise takes about 60 minutes.
When in doubt, make it smaller.

### Tests: cover more than the happy path

For every Build and Fix exercise, go through this checklist and test what applies:
empty input · single element · duplicates · `null` · boundaries (0, 1, max, just inside/outside a limit) ·
negative numbers · overflow · ordering/stability · large input · invalid arguments (with the exact exception type)
· immutability and defensive copies · state after a failed operation.

- **Randomized tests** for data structures and algorithms: fixed seed (`new Random(42)`), compare against the JDK
  or a tiny obviously-correct model, and put the step number in `.as(...)` so failures are reproducible.
- **Concurrency tests** use `practice.testkit.Concurrently` (threads start together; daemon threads; 8 s timeout).
  They must pass every time on the solution and fail reliably on the buggy version: use enough threads and
  iterations, and `@RepeatedTest` where a race is probabilistic. Never leave non-daemon threads blocked.
- **Timeouts:** every test gets 10 s and runs in its own thread (`testkit/src/main/resources/junit-platform.properties`).
  So don't set a `ThreadLocal`/`ScopedValue` in `@BeforeEach` and read it in the test.
- Keep a module's whole test run under about 30 seconds.
- Use AssertJ (`assertThat`, `assertThatThrownBy`), given/when/then layout separated by blank lines, and test one
  behavior per test.
- JUnit 6 puts text arguments of parameterized tests in quotes in display names (`"{0}"` shows `"abc"`).
  Use `@ParameterizedTest(name = "...", quoteTextArguments = false)` when the quotes hurt readability.
- Write non-ASCII characters in Java source as escapes when they're invisible (`﻿`, zero-width spaces),
  so nobody is confused by a character they can't see.

### Predict exercises

`Puzzles` holds small methods; `Answers` holds one typed constant per puzzle, initialised to `null`
(`Integer`, `Long`, `Double`, `Character`, `String`, `Boolean`, or an exercise-specific enum for outcomes like
"throws"). Tests call `practice.testkit.Predict.check(Answers.X, Puzzles.x())`. The solution fills `Answers` with
a one-line "why" comment each, and the README explains every puzzle inside a collapsed `<details>`.
See `java/j01-basics` J01-02.

### Write tests exercises

The given class is complete and correct, with Javadoc rules precise enough to test. The test file on `main` is a
skeleton: the `@DisplayName`, a short Javadoc explaining scoring, and `// TODO: J03-03`. Write 4–6 learner
mutants, each a different kind of mistake. See `java/j03-exceptions-testing` J03-03.

### Fix exercises

The code looks reasonable and compiles, but has 1–3 realistic bugs. The Javadoc describes the *intended* behavior;
the README frames it like a bug report ("Customers report that…"). Tests show the symptoms.

### Reference solutions

Idiomatic, modern Java 25 as it is written in good production codebases (see `docs/handbook/`). Add short
comments that explain **why**, more than production code would, because the learner compares their solution with
yours. Don't comment the obvious.

## Java style for exercises and solutions

- 4 spaces, max ~120 columns, no wildcard imports (static imports only for AssertJ/JUnit/Mockito helpers).
- `final` fields; immutable by default; records for plain data; static factories where they read better.
- Validate arguments at the boundary: `Objects.requireNonNull(x, "x")`, `IllegalArgumentException` with the bad
  value in the message.
- Return empty collections and `Optional`, never `null`, from public methods. `Optional` only as a return type.
- `var` when the type is obvious from the right-hand side.
- Javadoc on every public type and method of the exercise API; comments explain why, not what.
- No Lombok in Part 1.

## Verifying (do this before every commit that touches exercises)

On the `authoring` branch, from the repository root, with your exercise files committed:

```bash
scripts/solutions.sh apply java/j05-collections   # copy the reference solutions in
scripts/verify.sh solved j05                       # ✔ every test passes, every mutant caught
scripts/solutions.sh reset java/j05-collections   # back to the exercises
scripts/verify.sh unsolved j05                     # ✔ every exercise starts out failing
git status                                         # clean apart from your own changes
```

Gradle reuses test results when nothing changed (up-to-date checks and the build cache), so repeating a check
re-runs nothing unless you add `--rerun`: `scripts/verify.sh solved j08 --rerun`. Run modules with concurrency or
timing-sensitive tests at least five times that way (solved) and three times (unsolved) to catch flaky tests.
`./score j05` shows the learner's view. Never commit while solutions are applied; `scripts/solutions.sh apply`
refuses to run over uncommitted changes.

## Releasing

After both checks pass for every module: `scripts/release.sh "<message>"` on a clean `authoring` branch updates
`main` and `solutions`. Don't push; the learner pushes to GitHub themselves.

## Part 2: Spring Boot modules

Everything above applies, plus the rules below. Read `spring/BOOKSTORE.md` first: it's the contract for the domain,
schema, seed data, package layout and API conventions.

### Module layout

```
spring/s06-spring-data-jpa/
├── README.md                    lesson + exercise sections (same format as Part 1)
├── build.gradle.kts             plugins { id("practice.spring-exercises") } + the starters this module needs
├── compose.yaml                 MySQL for ./gradlew …:bootRun (modules with a database)
├── src/main/java/com/example/bookstore/…    the application at this module's checkpoint
├── src/main/resources/application.yml, db/migration/V1__…, V2__…
├── src/test/java/com/example/bookstore/…    tests, next to the code they test
└── src/mutants/<exNN-name>/     learner mutants (Write tests exercises only)
```

- **Each module is a complete, standalone Spring Boot application** (root package `com.example.bookstore`). Start
  from the maintainer template in `.authoring/bookstore-template/` (it exists only on `authoring`) and copy what the
  module needs: migrations, entities, repositories, error handling, test support. Keep names, packages and code
  style identical to the template, so modules feel like one evolving codebase.
- `practice.spring-exercises` provides Spring Boot's BOM, Lombok, `spring-boot-starter-test` and the scoring setup.
  The module's `build.gradle.kts` lists its starters explicitly (Boot 4 names: `spring-boot-starter-webmvc`,
  `-data-jpa`, `-flyway` + `org.flywaydb:flyway-mysql`, `-jdbc`, `-validation`, `-aspectj`, `-cache`,
  `-restclient`, `-security`, `-security-oauth2-resource-server`, `-actuator`; test starters end in `-test`;
  Testcontainers 2: `org.testcontainers:testcontainers-mysql`, `org.springframework.boot:spring-boot-testcontainers`;
  MySQL driver `com.mysql:mysql-connector-j`; Docker Compose support `developmentOnly("org.springframework.boot:spring-boot-docker-compose")`).
- Register the module in `settings.gradle.kts` (Part 2 list).

### Exercises are tickets

- **Tests live next to the code** in the application's packages (`com.example.bookstore.order.OrderApiTest`), not in
  `practice.sNN…`. The exercise is identified by the top-level test class's display name:
  `@DisplayName("S06-05 · The N+1 problem")`. Several test classes may share one exercise's display name.
- Each exercise is framed like a work ticket in the README ("Implement `POST /api/orders` …", "Bug: …"), with
  acceptance criteria. The tests are the acceptance criteria.
- **The application context must start on `main`.** Stubs throw `UnsupportedOperationException("TODO: S06-05")`
  only inside methods, never in constructors, `@Bean` methods or `@PostConstruct`: one failing context would fail
  every exercise in the module. When the bean wiring *is* the exercise (S01, S02), test it with
  `ApplicationContextRunner` or small dedicated contexts so each exercise fails on its own.
- Mutants name the exercise and the tests to run, because the package doesn't identify the exercise:
  ```properties
  exercise=S06-05
  tests=com.example.bookstore.order.OrderListApiTest
  audience=verification
  description=Loads the lines of each order with a separate query (N+1).
  ```
  A mutant can replace any class, including Spring beans; its classes shadow the real ones on the test classpath.

### Tests with a database

- Tests need Docker. They use the template's `TestcontainersConfiguration`: **one MySQL 9.7 container per test
  JVM**, shared by every application context, started with small memory settings.
- **Keep the number of distinct application contexts low**: Spring caches a context per configuration, and every
  new one costs seconds. Prefer the template's `@IntegrationTest` meta-annotation; avoid `@DirtiesContext` and
  one-off `@MockitoBean` combinations.
- **Leave the database as you found it.** The template's `@IntegrationTest` is `@Transactional`: each test, its
  `@BeforeEach` and its MockMvc requests share one transaction that is rolled back. Tests that need real commits
  (concurrency, after-commit events) opt out with `@Transactional(propagation = NOT_SUPPORTED)` and call
  `seedData.restore()` in `@AfterEach` (Flyway clean + migrate, about 0.25 s).
- Spring module tests run test methods on the calling thread (`practice.spring-exercises` sets JUnit's timeout
  thread mode to `SAME_THREAD`): Spring binds transactions to threads. The template's `TestThreadGuard` fails loudly
  if that setting is missing. Tests run at a fixed time (`TestClock`, 2026-10-15T00:00:00Z).
- Tests may rely on the seed facts documented in `spring/BOOKSTORE.md`; don't depend on undocumented seed rows.
- Count SQL statements with the template's `SqlStatementCounter` (N+1 tests).
- Keep a module's test run under about 90 seconds; mutants each start a fresh JVM and container, so prefer 2–4
  sharp verification mutants per exercise over many weak ones.

### Spring style

- Constructor injection only, with Lombok `@RequiredArgsConstructor` on beans; `final` fields.
- Lombok rules: `@Getter` and `@NoArgsConstructor(access = AccessLevel.PROTECTED)` on entities; no `@Setter` or
  `@Data` on entities; `@RequiredArgsConstructor` and `@Slf4j` on beans; records instead of Lombok for DTOs.
- Entities protect their rules with methods; no public setters; `@ManyToOne(fetch = LAZY)`; ids `Long` with
  `IDENTITY`; timestamps `Instant`.
- `@Transactional` on service methods (`readOnly = true` for queries), never on controllers.
- Configuration through `@ConfigurationProperties` records, not `@Value`.
- Handbook pages for Part 2 (in `docs/handbook/`): `spring-layering.md`, `jpa-entities.md`, `transactions.md`,
  `rest-api-design.md`, `configuration.md`, `logging-and-observability.md`, `lombok.md`, `spring-testing.md`,
  `security.md`.

### Verifying Part 2 modules

Same commands with the `spring/` path: `scripts/solutions.sh apply spring/s06-spring-data-jpa`,
`scripts/verify.sh solved s06`, and so on. Docker must be running.
